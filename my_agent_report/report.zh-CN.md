# 从 Agent 推广到端到端交付：米哈游的决策与反思

**语言：** 简体中文 | [英文版](report.md)

**状态与范围：** 面向管理层审阅的工作草稿。我以在米哈游的 agent 开发经历，以及 2025 年 11 月至 2026 年 7 月的观察为基础。计划中的一年回顾，其完整起止时间及我的正式职位名称仍待确认。

## 核心概览

我看到米哈游从少量 agent 探索迅速进入激进的 All In 阶段。员工开始广泛使用 agent 处理个人单点任务，公司则希望依靠现成框架和员工编写的 skill，把这些任务串成完整工作流。我的判断是，这一路线忽略了面向 agent 的公司级配套基建。广泛采用和 MCP 覆盖扩张的同时，可用性、权限和交付问题逐渐显现。我也看到，公司随着目标变化，召集了不同背景的人员。

到 5—7 月，公司态度不再那么激进，一线和部门则更关注 harness 工程以及长任务需要的基础设施。MCP 得到重构，知识检索、权限和记忆能力逐步建设。一个部门框架提供开发、部署和验证能力，另一个项目支持个人记忆迁移。如何把单点提效串成多人或多个 agent 参与的工作流，仍是探索中的目标。

这条主线可以概括为：**All In Agent、忽略配套基建 → 以个人单点提效为直接着力点 → 加强 agent 基建 → 尝试串联端到端工作流**。这些重点存在重叠：工作流闭环目标早已提出，4 月 Project S 已尝试团队级串联，早于 5—7 月的基建完善。以下案例按实际时间展开，尚不能据此认定全公司已经实现工作流闭环。

| 案例 | 时段 | 决策重点 | 我的回顾中的关键结果 |
| --- | --- | --- | --- |

| 2 | 2026 年 1 月 OpenClaw 热潮之后 | 通过 Echo 降低通用 agent 使用门槛 | 获得广泛采用，尤其受到非研发人员欢迎。 |

**分析依据：** 我参与了数据团队的 agent 工作、12 月平台讨论、成本事件复盘、Project S 工作流适配，以及个人记忆项目的推进。其他进展来自我的观察和回顾，记录于 2026 年 9 月 17 日。下文区分公司立场、我的个人评价和可能解释；标注为**暂定分析**的内容及决策选项，仍是待我审阅的草案。内部进展尚未独立核实，公开来源只支持来源表注明的外部背景。

## 案例 1 — 2025 年 11—12 月：从有限基础出发讨论共享平台

### 决策与行动

我于 2025 年 11 月加入米哈游数据团队，从事 agent 开发。据我当时了解，我参与的项目是全公司为数不多的 agent 项目之一。公司已有私有化部署的 Dify，但在我观察的时段内始终没有受到多少关注。到 12 月，据我了解，公司级基建仍只有 LLM 网关和 Dify，另有少量项目。

**早期人员方向：** 公司起初招募有 agent 开发经验的人，自研 agent 运行时框架。具体招募日期和人员安排仍待补充。

我与公共团队负责人讨论了服务端通用 agent 平台、skill hub 和知识库，希望在未来几个月帮助员工迁入自己的业务流程，或更好地完成端到端工作。我将这位负责人的职级描述为“创始人减一”，认为讨论在一定程度上反映了高层想法。这一描述不代表已确认具体汇报关系；英文中的“shared team”是暂定译法。

### 可能原因

**已记录的目标：** 为员工工作流提供共用平台和配套能力。

**暂定分析：** 当 agent 项目还很少时，共享平台可能是把能力复用到全公司的路径。这是对方案动因的一种解释，尚不是有记录的高层表述。仅凭 Dify 关注有限，还不足以判断它能否支持这些目标，也无法解释它受到关注有限的原因。

作为比较，我更早任职的字节跳动从 2023 年底就将 LLM 用于客服和内部研效，之后向其他场景扩展。到 2025 年底，一些工具已经能够闭环完成某些长任务，我认为效果很好。因此，我认为米哈游起步较晚。这是个人比较判断，不是行业排名；早期 LLM 应用也不都等同于 agent。我入职米哈游时认为 Sonnet 4.5 是当时最强的模型，其 2025 年 9 月 29 日发布日期只能确认时间背景，不能证明这一排名。

### 关键结果

- 讨论了共享基建和平台方向；正式批准、资源、交付及与 Dify 的关系仍待确认。
- 在我的观察中，Dify 的可用并未转化为多少关注；使用与业务价值尚未量化。
- 数据团队项目是早期 agent 实践之一，但具体目标、交付节点及结果仍待展开。

*依据：U01、U02、U10、S01。*

## 案例 2 — 2026 年 1 月 OpenClaw 热潮之后：Echo 降低使用门槛

### 决策与行动

在我记忆中 2026 年 1 月 OpenClaw 在国内走红之后，另一个团队独立、自发地发起了 Echo，一种运行在用户客户端上的通用 agent。它与 12 月的平台讨论属于不同项目线。

它的产品形态让我想到 Kimi Claw；回顾时，也让我联想到记录这段经历的 2026 年 9 月所见的 ChatGPT 客户端。这些只是产品类比，不能确定 Echo 的上线日期、架构或技术依赖。

### 可能原因

**我的判断：** Echo 的客户端 UI 大幅降低了开始使用所需的成本，尤其是对非研发同事。我认为这是它得到广泛使用的重要原因。

**暂定分析：** 易上手的客户端可能让员工更直接地体验通用 agent 的价值。这里的对比没有控制场景、用户群和推广条件，因此不能据此判断客户端 agent 普遍优于服务端平台。

### 关键结果

- 我观察到广泛使用，尤其是在非研发人员中，并认为 Echo 是公司层面的采用成功。
- Echo 是我这段经历中的转折点；其成功是否直接促成了后续某项管理决策，仍待确认。
- 留存、具体任务节省的时间、业务影响、正式支持及后续路线，仍需证据。

*依据：U03。S02、S03 仅提供命名和产品时间背景，不独立佐证 Echo 推广。*

## 案例 3 — Echo 之后的两三个月：All In 框架与 Skill

*我将个人研效重点定位在 2026 年 2—4 月。此前回顾中的更广泛扩张发生在 Echo 转折之后两三个月，其确切起止及成本事件复盘日期仍待明确。本案例与后面的 3—4 月案例存在重叠。*

### 决策与行动

我看到公司对 LLM 和 agent 转为非常激进，并投入大量资源。据我理解，当时的方向是：现成框架已经足够好，无需继续研发通用 agent；人人都可以通过编写足够完备的 skill 创造 agent，最终把员工的工作串成端到端流程。

二—四月，公司的直接重点是提升单个员工的研效。在我的观察中，熟悉业务背景的同事利用 agent 客户端，在这方面做得更好。与此同时，公司叫停了**几乎所有运行在服务端上的 agent 项目**。这些项目与案例 4 中部门 OpenClaw 部署的重叠范围仍待明确。

各部门对 OpenClaw 进行二次封装，员工则把零散任务迁入 agent，并接入办公 IM chatbot。对于下述成本事件，公司将费用定性为探索 LLM 的必要代价。我参与了那次复盘。

### 可能原因

**我理解的公司立场：** 已有框架降低了再研发通用 agent 的必要性；员工编写的 skill 被寄望于承载业务工作，并支持更大范围的串联。

**暂定分析：** Echo 的广泛使用和足够成熟的现成框架，可能让快速扩张看起来可行。这一路线可能较快动员大量员工参与。需要检验的假设是，足够完备的 skill 是否能把有用的个人任务，转变为跨人员、跨 agent 的可靠工作流。采用规模本身无法验证这一点。框架与 skill 路线的正式传达来源仍待补充，我对公司容忍这次成本事件的个人评价也仍待展开。

### 关键结果

- 我的判断是，员工单点提效问题在**两三个月内**迅速得到解决。具体覆盖哪些任务、如何判断已经解决，以及量化收益，仍待补充。
- 部门层面出现了至少四到五个 OpenClaw 封装项目，单点任务应用和 IM 接入变得广泛，但全公司工作流闭环尚未得到确认。
- 一位员工使用 Opus 4.6 探索多 agent 协作，**一天产生人民币 200 万元 token 费用**。网关未限制这次实验的用量，实验也未限制 agent 数量及 agent 间历史消息数据量。我将消耗与这些缺失的限制联系起来；本报告尚无账单及成本分解。
- 我参与的公司复盘指出：网关限额逻辑不完善，路由问题导致 **KV cache 命中率低**，以及缺少支持 **multi-agent 和 agent 间（A2A）协作**的基础设施。
- 公司接受了这笔探索成本，但实验的技术与业务价值、整改及其效果仍未明确。接受费用不能等同于实验成功。

*依据：U04、U05、U10。S04 仅提供 Opus 4.6 发布日期，不核实内部事件。*

## 案例 4 — 2026 年 3—4 月：接入广泛，Agent 基建仍不足

### 决策与行动

公司级基建快速扩张，几乎所有内部系统都设计了 MCP 接口，许多实现通过封装现有服务 API 迅速提供能力。在我对这一阶段的回顾中，个人和团队 agent 应能访问哪些系统仍未解决。

更广泛的推进思路依然强调人人都能创造 agent。我的判断是，尽管 MCP 覆盖扩大，公司仍忽略了面向 agent 工作流的公司级基建。

### 可能原因

**我的判断：** 很多封装沿用了适合人类使用、却不适合 agent 的接口设计。我将这种基建缺口与当时普遍感到 AI 项目推进不及预期联系起来。

**暂定分析：** 复用现有 API 可以快速暴露工具，但“有能力可调用”可能比“长任务中真正可用且权限明确”更容易做到。Skill 可以描述工作，却未必能解决这些底层条件。这是待检验的解释，尚不是公司正式结论，也不能证明每个项目为何停用。

### 关键结果

- 我认为绝大多数 MCP 实现质量很低。读取数据时，agent 需要反复调用工具、调整分页参数，消耗大量上下文；具体调用次数及任务影响尚未测量。
- 个人和团队 agent 的权限依然不清晰，广泛接入并没有解决谁可以访问什么的问题。
- 我记得 3—4 月大家普遍感到 AI 项目推进不及预期。这是我对群体感受的观察，并非调查或覆盖每个项目的量化结论。
- 部门 OpenClaw 部署几乎全部下线，**直接停用**。具体原因、决策者、与此前项目数的对应关系及是否包括 Echo，仍待明确。

*依据：U06、U08。案例 6 记录 5—7 月的后续重构。*

## 案例 5 — 2026 年 4 月：Project S 尝试通用 Harness 与数据飞轮

### 决策与行动

公司态度依然非常激进时，一位米哈游创始人亲自推动了 Project S。我将它理解为一次结合**通用 harness 框架与团队记忆数据飞轮**的尝试。它基于 Claude Code，打通办公 IM，目标是把一个团队或部门每个人的工作流程都迁入系统。

**我参与的落地工作。** 在数据团队期间，我花了大约两个月承担 FDE（Forward-Deployed Engineer）职责，将其他同事的工作流程适配到 Project S。这段工作的具体起止时间仍待确认。我尝试支持的完整数据工作流包括：

```text
理解需求
  -> 收集需求上下文
  -> 设计数据埋点
  -> 接收埋点回流数据
  -> 设计数仓表
  -> 跑数验证
```

其预期设计结合了：

- 从人与人、人与 agent 的对话、会议、文档及其他工作材料中形成团队记忆。
- 对全体团队成员可见的记忆，以及拥有所有成员数据权限的 agent。
- 把所有办公入口集中到 IM，让 agent 获取完整的工作流上下文。

**我所了解的架构。** 系统有一个 pod 池，每个用户对应一个 pod。每个 pod 内有一个 Claude Code coordinator，将用户请求分配给 worker、researcher 等不同角色的 Claude Code agent。以下为逻辑示意，两家公司各组件的实际部署范围仍待补充。CC 指 Claude Code。

```text
Pod 池：每个用户一个 pod
|
+-- 用户 1 -> Pod 1
|               |
|               +-- 用户请求 -> Coordinator（一个 CC）
|                                  |
|                                  +--> Worker（CC）
|                                  +--> Researcher（CC）
|                                  +--> 其他角色（CC）
|
+-- 用户 2 -> Pod 2（内部结构相同）
+-- ...   -> ...  （内部结构相同）

会话记录 -------------------+
                            +--> 采集者
Agent 所在 IM 群聊记录 -----+       |
                                    | 同步
                                    v
                              Vault Manager
                                    |
                           向量化检索的相似度
                                    |
        +---------------------------+------------------------+
        | 高                        | 中                     | 低
        v                           v                        v
  丢弃新采集内容             与已有节点合并          新建节点并建立节点间联系
                                    |                        |
                                    +-------------+----------+
                                                  v
                                          Vault（团队记忆）
                                                  ^
                                                  |
                                               定时巡检
                                          合并 / 更新 / 删除
```

采集者收集会话记录和 agent 所在 IM 群聊的记录，再同步给 Vault Manager。后者根据向量化检索相似度处理新采集内容：**相似度高则丢弃，中等则与已有节点合并，低则创建新节点并建立节点间联系**。Vault 还有定时巡检，负责记忆数据的合并、更新和删除。

数据飞轮的目标，是把持续产生的工作记录转化为可复用的团队上下文。记忆如何被 agent 检索复用、会议与文档如何接入，以及是否改善后续任务结果，仍待补充。

据我了解，创始人先在自己的另一家 LLM 公司 Anuttacon 推行。我将 Anuttacon 描述为权限体系相对简单的初创公司，初期推进较顺利。

### 可能原因

**我所了解的设计目标：** 在不同项目中复用通用 harness，以 IM 为共同入口，从团队工作中持续积累上下文。

**我的判断：** 较简单的权限有助于 Anuttacon 推进；在米哈游，复杂权限是最大障碍。我认为项目非常理想化，对团队全员开放记忆、把所有办公入口迁入 IM 的要求，对这一环境都过于激进。具体而言，我将未能成功推广归因于三项设计缺口：

1. **把 agent 定义为团队员工，却没有设计相应的权限体系。** 员工式的角色定位及预期访问能力，缺少对应的 agent 权限设计。
2. **团队记忆没有隔离。** 团队记忆系统没有建立该环境所需的隔离；具体应隔离哪些边界，仍待展开。
3. **通用 harness 层能力太弱。** 以记录本次回顾时的判断，我认为目前并不存在一套能够适配任何项目的 harness 框架。这是我的技术判断；本报告现有证据尚不包含系统性的框架对比。

**我在数据工作流适配中的反思：** 把这些环节串联起来，需要 agent 反复修改、自迭代并验证自己的产物，对 harness 和 agent 基础设施的要求极高。另一个困难是，**并不是每个环节都有清晰、可量化的验收标准**。我的判断是，当单点任务串成端到端工作流时，agent 可能在任一验收标准模糊的环节偏离原始任务目标。

**暂定分析：** 初创公司的进展可能让方案看起来能够迁移。对比提示，跨组织推广前，需要评估 agent 的权限、记忆边界，以及具体工作流所需的 harness 能力。在我的描述中，每用户一个 pod 与团队记忆未隔离同时存在，因此不能把运行结构当作记忆已隔离的证据。现有材料无法单独识别各项缺口的贡献，也不能据此认定团队记忆本身不可行。

### 关键结果

- 在 FDE 工作中，我感到 Project S 在真实单点需求上表现不错，例如设计一个数仓表。这是我的定性评价，任务结果的量化数据仍待补充。
- 根据我的回顾，Anuttacon 初期推进较顺利；尚不能确认已完整迁移，或取得了量化业务价值。
- 米哈游未能推进预期推广。项目最终状态、试点范围及是否仍有部分功能在使用，尚不清楚。
- Project S 较早尝试通过可复用的 harness 和持续积累的记忆，把个人辅助串成团队工作流。本次回顾尚无证据证明，这条记忆处理链路改善了后续任务，或形成了有效运转的数据飞轮。上述失败解释属于我的评价，尚不是公司正式复盘结论。

*依据：U07。S05 只支持 Anuttacon 的名称及其自述研究方向。*

## 案例 6 — 2026 年 5—7 月：为串联单点提效建设基础设施

### 决策与行动

我观察到，公司层面不再那么激进，但一线员工与部门普遍开始推进 harness 工程：使用 Codex、Claude Code 或 pi agent 时，探索什么上下文能够更好地约束 agent 完成长任务。大家也研究多人或多个 agent 参与的端到端交付，需要哪些基础设施。

公司内部也重新开展了各类 agent 项目，重点从研发 agent 运行时框架，转向**在现有成熟框架上做 harness 工程**。公司此时需要的是有 **ToB 经验**的 agent 开发者，承担类似 FDE（Forward-Deployed Engineer）的职责。

这三个月里，之前仓促上线的 MCP 基本都重构了，并补充或建设了知识库检索、agent 权限体系和 agent 记忆能力。基建工作开始更具体地处理 agent 如何使用知识、访问系统和延续上下文。

两个部门项目让这些建设有了具体形态：

**基于 OpenCode 的交付框架。** 框架提供端到端开发、部署、上线能力。由于同时支持前后端部署，研发可以让 agent 通过 browser use 或 Playwright 验证产物。这说明具备一条可用的验证路径，尚不是某次测试成功或无人生产发布的记录。

**我推进的个人记忆系统。** 我推进了一个解决个人在多个端、多个 agent 间协作问题的项目。记忆可以从一个端迁移到另一个端，也可以从一个 agent 迁移到另一个 agent。这解决个人工作连续性的需求，与 Project S 的团队全员可见性不同。两个系统的技术关系，以及记忆项目与我最初参与的数据团队项目的关系，仍待确认。

### 可能原因

**我对变化的理解：** 我将重新开展 agent 项目，与案例 3 中个人单点提效问题的快速解决联系起来。

**暂定分析：** 前面的案例呈现了“创造一个 agent”与“提供足以让它完成工作的条件”之间的差距。5—7 月的重点可能反映了对这些条件的进一步重视：相关知识、可用工具、明确的访问权限、持续的上下文，以及验证产物的方式。这些能力结合起来，可能让单点任务的串联更具可行性。ToB 经验也可能有助于案例 5 中我的 FDE 工作所涉及的流程适配和验收沟通。

OpenCode 案例也提示，除了生成和部署，验证能力可能影响研发接受度。可运行的应用，以及让 agent 检查它的方式，可能让研发更容易评估生成的产物。这些是对建设重点和项目反馈的可能解释；公司态度变化的原因、正式政策或资源变化，以及与此前整改的关系仍待明确。

### 关键结果

- 我观察到了基建重构和配套能力补充。上线范围及对任务完成的量化影响仍待明确；重构不代表此前每个问题都已解决。
- OpenCode 二开项目起初受到非研发同事欢迎，补充 agent 端到端验证后，也获得了**研发同事一定程度的接受**。
- 我认为自己推进的记忆项目也是受欢迎的部门实践。它提供了**跨端、跨 agent 的记忆迁移能力**，采用数据和业务影响尚未量化。
- 这些项目提供了与工作串联相关的能力，但多人、多 agent 可靠工作流的更大目标仍在探索。本次回顾尚不能证明全公司已完成这一转变。

*依据：U09、U10。基建与部门实践同处 5—7 月，内部的具体先后及交付日期仍待明确。更广泛地重新开展 agent 项目及人员需求变化的具体日期，也仍待确认。*
