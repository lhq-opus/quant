# Agent 推广与项目落地：我在米哈游的经历与思考

**语言：** 简体中文 | [英文版](report.md)

**状态：** 面向管理层审阅的工作草稿。案例结果和支持证据仍在补充；分析假设与决策选项保留为待我审阅的草案。

**目的：** 我希望通过回顾米哈游的 agent 推广经历，包括我在数据团队的工作，为当前公司的 AI 决策提供参考。我更早在字节跳动的经历作为比较背景。

**回顾时间范围：** 计划回顾约一年的经历，确切起止仍待确认。当前米哈游叙述从我于 2025 年 11 月入职延伸至 2026 年 7 月：早期平台讨论、Echo 的出现及后续扩张、3—4 月的基建与落地问题、创始人于 4 月推动 Project S，以及 5—7 月的 harness 工程和配套基建建设。具体项目、推广与结果日期仍待明确。字节跳动的对照覆盖 2023 年底至 2025 年底；Anuttacon 作为 Project S 案例内的比较对象。

## 执行摘要

我于 2025 年 11 月加入米哈游数据团队，从事 agent 开发。据我当时了解，全公司的 agent 项目很少，我参与的项目正是其中之一。公司内部已有私有化部署的 Dify，但在我观察的整个时段内，它受到的关注一直有限。

到 12 月，据我了解，公司层面的 agent 基础设施仍只有 LLM 网关和 Dify，另有零星项目。我与米哈游公共团队负责人讨论过建设服务端通用 agent 平台、skill hub 和知识库，希望在未来几个月支持员工的业务流程和端到端工作。这次讨论的批准、资源、实施及结果仍待补充。

我认为 Echo 是一个重要的采用转折。继我记忆中 2026 年 1 月 OpenClaw 在国内走红之后，另一个项目团队独立开发了运行在员工客户端上的通用智能体。我观察到它在公司内被广泛使用，尤其受到非研发人员欢迎，并认为它在公司层面很成功。在我看来，客户端 UI 大幅降低了上手成本。

随后两三个月，我看到公司在 LLM 和 agent 上转为非常激进。部门层面出现了至少四到五个 OpenClaw 二次封装项目，员工大规模将单点工作迁移至 agent，并接入办公 IM chatbot。据我理解，公司当时的立场是：现成框架已经足够好，没有必要继续研发通用 agent；应由员工编写完备的 skill，最终把单点任务串成覆盖所有人工作的完整流程。单点任务的采用已经可见，更广泛的流程闭环是否实现仍待明确。

公司为此投入了大量资源。我记得其中一位员工使用 Claude Opus 4.6 探索多 agent 协作，一天产生了人民币 200 万元的 token 费用。据我了解，当时网关没有限制这次实验的用量，实验也没有限制 agent 数量和 agent 间历史消息数据量。我参与了公司的复盘。公司将这件事视为探索 LLM 的必要代价，同时指出网关限额逻辑不完善、路由问题导致 KV cache 命中率低，以及缺少支持多 agent 和 agent 间（A2A）协作的基础设施。支持记录、核算口径、实验结果和后续整改仍待补充。

2026 年 3—4 月，我观察到公司级 agent 基础设施快速建设，几乎所有内部系统都设计了 MCP 接口。我认为其中绝大多数实现质量很低：很多直接对现有服务 API 进行封装，以快速提供 MCP 能力，沿用了适合人类使用、却对 agent 不友好的设计。例如，agent 读取数据时需要反复调用 MCP、调整分页参数，消耗大量上下文。我也认为权限体系设计不充分；我对这一阶段的回顾记录了个人 agent 和团队 agent 应能访问哪些系统的问题仍未解决。

在我的回顾中，3—4 月大家普遍感到 AI 项目的推进不及预期。据我理解，公司当时认为人人都可以创造 agent。我认为公司忽略了从公司层面提供面向 AI 和 agent 工作流程的基础设施，并将这一缺口与推进不及预期联系起来。在此期间，各部门部署的 OpenClaw 几乎全部下线并停用。每次停用的具体原因仍待补充。

到 2026 年 4 月，我看到公司对 agent 仍然非常激进。一位米哈游创始人亲自推动 Project S，项目基于 Claude Code、接入办公 IM，目标是迁入一个团队或部门的全部工作流程。设计中，团队记忆对全体成员可见，agent 拥有每位成员的数据权限。根据我的了解，该项目先在这位创始人的另一家 LLM 公司 Anuttacon 推行，较简单的权限体系使初期推进更顺利。在米哈游，我认为复杂权限是最大障碍，全员可见的记忆和所有办公入口集中到 IM 的要求也过于激进。预期的推广未能推进，最终范围和状态仍待澄清。

2026 年 5—7 月，我观察到公司层面不再那么激进，一线员工与部门则普遍探索 harness 工程：使用 Codex、Claude Code、pi agent 时，应提供怎样的上下文，才能更好地约束 agent 完成长任务。大家也探索多人或多个 agent 参与的任务端到端交付所需基建。此前仓促上线的 MCP 基本都进行了重构，并补充或建设了知识库检索、agent 权限及记忆能力。

这一时期有两个部门项目，在我看来都很受公司内同事欢迎。一个基于 OpenCode 二次开发的框架提供端到端开发、部署、上线能力，起初受到非研发同事喜爱，增加 agent 端到端验证能力后，也获得了研发同事一定程度的接受。它提供前后端部署能力，研发可以让 agent 通过 browser use 或 Playwright 验证产物。另一个是我推进的记忆系统，支持个人跨端、跨 agent 协作，使记忆可以在不同端和不同 agent 之间迁移。详细交付结果和采用指标仍待补充。

与我更早任职的字节跳动相比，我认为米哈游在 LLM 和 agent 应用方面起步明显偏晚。字节跳动从 2023 年底开始将 LLM 用于客服和内部研效，并逐步扩展到其他领域。到 2025 年底，一些工具已经能够闭环完成某些长任务，我认为效果非常好。详细结果及两家公司差异的原因仍需进一步分析。

## 背景与范围

本次回顾记录于 2026 年 9 月 17 日。报告中的内部进展和公司立场尚未获得独立佐证；公开来源用于核对外部产品时间线、Anuttacon 的名称及其自述研究方向，不核实内部推行情况。我的正式职位名称和完整任职日期仍待补充。

全文区分我参与的事情、我观察或了解到的公司情况，以及我的个人判断。同时区分早期 LLM 应用与能够执行较长任务的 agent；字节跳动的经历不意味着其 2023 年的所有应用都是 agent。

### 2025 年 12 月——我参与的共享 agent 平台讨论

我与米哈游公共团队负责人进行过交流，其职级用我的表述是“公司创始人-1”。公共团队在英文中暂译为 shared team，正式英文名称仍待确认。职级描述本身不代表具体的汇报关系。

我们讨论了如何在未来几个月建设以下能力：

- 在服务端运行的通用 agent 平台。
- 包括 skill hub 和知识库在内的支持基础设施。
- 让员工能够将自己的业务流程迁移到平台，或借助平台更好地完成端到端工作。

考虑到这位负责人的职级，我认为这次讨论在一定程度上反映了当时高层的态度与规划。这是一场规划讨论。已约定的行动项、负责人、资源、排期、交付结果及后续组织反思仍待补充；拟议平台与 Dify 是扩展、替代还是并存关系，也仍待明确。

### 2026 年 1 月 OpenClaw 热潮之后——Echo 与更广泛的采用

Echo 来自另一个项目团队的自发探索，独立于 12 月的平台讨论。我认为它获得广泛使用，尤其是在研发以外的员工中，是公司 agent 采用情况的一次明显变化。

两条项目线有不同的起源。它们后来如何使用共享基础设施、服务端方案的进展，以及针对 Echo 的支持和决策仍待补充。C03 记录了 Echo 的采用情况及我的解释。

### 随后两三个月——围绕框架和 skill 的激进扩张

我观察到公司对 LLM 和 agent 的投入意愿明显增强。部门层面出现了至少四到五个 OpenClaw 二次封装项目。员工开始大规模将零散、单点工作迁移至 agent，并接入办公即时通信 chatbot。

据我理解，公司当时认为市场上已经有足够好的框架，一切通用 agent 都没有必要继续研发。重点转向复用框架，并由员工编写完备的 skill，最终将跨员工的工作串成完整流程。

公司在这一方向上投入了大量资源。在此期间，C05 中的多 agent 实验一天产生了 200 万元人民币的费用，公司最终将其定性为探索 LLM 的必要代价。我参与了公司的复盘，其中指出网关限额逻辑不完善、路由问题导致 KV cache 命中率低，以及缺少支持多 agent 和 A2A 协作的基础设施。这里记录的是公司的评价与反思。复盘日期、后续行动及我个人对这一回应的评价仍需在本稿中进一步展开。

框架与 skill 路线的正式来源和适用范围仍待澄清。它对具体项目，包括 12 月方案和 Echo 的影响，以及流程串联的实际结果仍待明确。

### 2026 年 3—4 月——基建快速扩展与推进不及预期

我观察到公司级基础设施进入快速建设期，几乎所有内部系统都设计了 MCP 接口，很多通过封装现有服务 API 快速提供 MCP 能力。

在我看来，其中绝大多数实现质量很低。既有设计未能很好适配 agent：读取数据时，分页要求 agent 反复调用工具、调整参数，消耗大量上下文。权限设计也仍不充分，个人 agent 和团队 agent 应能访问哪些系统一直没有明确。C06 进一步展开这些观察。

据我理解，公司当时认为人人都可以创造 agent。我的整体判断是，尽管 MCP 覆盖面迅速扩大，公司仍忽略了公司级 AI 原生基础设施。我将这一缺口与 3—4 月大家普遍感到 AI 项目推进不及预期联系起来。在此期间，部门 OpenClaw 部署几乎全部下线并停用，具体见 C04。

对基建的评价和因果解释属于我个人；普遍感受也是我的观察，并非调查结果或公司正式复盘。具体停用原因和决策仍待补充。这一时期与更广泛扩张阶段的重叠、相对于成本事件复盘的时间关系，以及与复盘整改的关联仍未明确。

### 2026 年 4 月——创始人亲自推动 Project S

我看到公司的激进态度延续到了 4 月，一位米哈游创始人开始亲自推动 Project S。项目基于 Claude Code，做了我所说的“harness 工程”，并打通办公 IM。它希望将一个团队或部门的全部工作流程迁入同一系统，配合共享团队记忆，并让 agent 拥有每位团队成员的数据权限。

根据我的了解，创始人先在自己的另一家 LLM 公司 Anuttacon 推行该项目。我将其初期推进更顺利归因于初创公司的权限体系较简单。在米哈游，预期的推广未能推进。我认为复杂权限是最大障碍，团队记忆全员可见和所有办公入口集中到 IM 的要求也过于激进。C07 分别记录设计、两家公司的推行差异及我的评价。

创始人的参与是我回顾中的具体高层行动。Project S 与此前框架和 skill 路线、Echo、12 月平台讨论及成本事件复盘的关系仍未明确。

### 2026 年 5—7 月——公司态度趋缓，部门继续推进工程实践

我观察到，公司层面相比前几个月不再那么激进。一线员工和部门则普遍将 harness 工程作为探索方向。在我描述的实践中，这指的是使用 Codex、Claude Code 或 pi agent 时，探索该提供怎样的上下文，才能更好地约束 agent 完成长任务。大家也研究当多个员工或多个 agent 参与时，任务端到端交付需要什么基础设施。

我将这三个月视为完善 agent 基建的时期。之前仓促上线的 MCP 基本都进行了重构，并补充或建设了知识库检索能力、agent 权限体系和 agent 记忆系统。C06 记录了此前基建问题的后续处理；具体质量和权限问题解决到何种程度，仍需证据。

部门项目继续获得采用。C08 记录了 OpenCode 二开框架从开发到上线的能力，以及非研发和研发同事的接受变化。C09 记录了我推进的个人跨端、跨 agent 记忆系统。公司态度趋缓属于我的观察，正式政策、资源变化及转变原因仍待补充。这些建设与此前成本事件复盘的关系也尚未确认。

### C03 — Echo：获得广泛使用的客户端通用智能体

**背景与产品：** 在我的回顾中，Echo 出现在 2026 年 1 月 OpenClaw 国内热潮之后，由另一个项目团队独立、自发发起。它是运行在用户客户端上的通用智能体。我觉得其产品形态与 Kimi Claw 接近；回头看，也类似于我在 2026 年 9 月记录这段经历时的 ChatGPT 客户端。

这些属于概括性的产品类比。Echo 的启动、上线和推广日期、实现方式及技术依赖仍待明确。1 月的背景不能确定 Echo 在 1 月上线，客户端应用本身也不意味着模型推理完全在本地运行。

**我的评价：** 我观察到 Echo 在米哈游内部被广泛使用，尤其受到非研发人员欢迎，认为它在公司层面是非常成功的采用案例。我将其广泛使用的重要原因归于客户端 UI 大幅降低了上手成本。这是我对结果的解释；本稿尚未纳入对比上手成本的测量，或能够单独识别 UI 影响的证据。

**待补证据：** 用户数、采用比例、留存、具体流程、生产力和业务结果、团队身份、分发与支持、后续决策及共享基建连接。12 月平台方案的后续状态仍是单独的待解问题。

### C04 — 部门级 OpenClaw 扩张与后续停用

**我的观察：** Echo 转折之后两三个月，部门层面出现了至少四到五个 OpenClaw 二次封装项目。员工大规模将单点工作迁移到 agent，并接入办公 IM chatbot。我看到公司投入了相当大的成本，但本稿尚未纳入总预算。

**我理解的公司方向：** 现成框架被认为已足够好，公司认为人人都可以创造 agent。预期由员工编写完备的 skill，使分散任务最终串成覆盖员工工作的完整流程，无需继续研发通用 agent。

**后续结果：** 2026 年 3—4 月，部门 OpenClaw 部署几乎全部下线并停用。我也记得这一时期大家普遍感到 AI 项目推进不及预期。早期的扩张和单点任务采用，随后出现了大范围停用；跨员工完整流程的更大目标是否实现仍未确认。

**我的反思与待补证据：** 我将推进不及预期归因于公司鼓励人人创造 agent，却忽略了共享 AI 原生基础设施。这是我对这一时期的解释，尚不是每个部署停用的已确认原因。项目和部署名称、部门、停用日期与决策、是否包含 Echo，以及与此前至少四到五个项目的对应关系仍待明确。IM 产品、skill 质量、跨团队复用、已经交付的任务结果、运行成本和流程成效也仍需证据。

### C05 — 据我了解单日花费 200 万元人民币的多 agent 实验

**我了解的事件：** 在扩张阶段，一位员工使用 Claude Opus 4.6 探索多 agent 协作，一天内产生了 200 万元人民币的 token 费用。这一数字是费用金额，其计费和核算口径仍需明确。

**我对消耗限制的了解：** 公司 LLM 网关没有限制这次实验的用量，实验也没有限制 agent 数量和 agent 之间传递的历史消息数据量。我将高额消耗与这些限制缺失联系起来。本稿尚未纳入日志或各因素对成本贡献的分解。

**我参与的公司复盘：** 我参与了公司对这次事件的复盘。公司最终将这笔支出视为探索 LLM 的必要代价，公司的反思包括：

- LLM 网关的限额逻辑不完善。
- 网关路由逻辑存在问题，导致 KV cache 命中率低。
- 缺少服务于多 agent 和 A2A 协作的基础设施。

以上是我参与复盘时公司提出的发现。本稿尚未纳入复盘记录、日志、缓存命中率测量或成本分解，无法对这些发现进行独立评估。具体基础设施缺口，以及后续整改、负责人、实施日期和结果仍待补充。

**待评估：** 实验尝试的任务、技术结果及业务价值仍未明确。复盘指出了基础设施问题，但仅凭这些发现仍不足以判断实验整体的成功或失败。事前预算授权也仍待补充。事件、金额及复盘发现依据我的回顾。Anthropic 于 2026 年 2 月 5 日发布的 [Opus 4.6 公告](https://www.anthropic.com/news/claude-opus-4-6)仅提供模型时间背景。

### C06 — MCP 与权限：快速铺开后的基础设施重构

**我的观察：** 2026 年 3—4 月，公司级 agent 基础设施快速建设，几乎所有内部系统都设计了 MCP 接口。很多实现直接封装现有服务 API，以快速提供 MCP 能力。系统清单、生产上线范围及实际使用情况仍待补充。

**我对接口质量的评价：** 我认为其中绝大多数实现质量很低。在我看来，直接封装现有 API 沿用了适合人类使用、却对 agent 不友好的设计。通过分页接口读取数据时，agent 需要反复调用 MCP 并调整分页参数，消耗大量上下文。这就是我所举分页例子的具体负担。目前尚未记录具体系统、任务、数据量、调用次数和上下文消耗量；这一评价针对我所接触的实现。

**早期推广中的权限缺口：** 我认为权限体系设计不充分。我对 3—4 月的回顾记录了个人 agent 和团队 agent 应有权访问哪些内部系统的问题仍未解决。两类 agent 的定义、具体访问问题，以及各项问题何时解决，仍待明确。C07 提供了涉及团队数据访问与共享记忆的案例。

**5—7 月的后续建设：** 此前仓促上线的 MCP 基本都重构了。这三个月也补充或建设了知识库检索、agent 权限及 agent 记忆能力。具体接口改动、权限体系覆盖范围和改进前后的任务结果仍待补充。

**结果与反思：** 我观察到了广泛铺开、可用性和权限问题，以及后来的基建重构。重构本身尚不能证明此前所有问题已经解决。任务完成、上下文消耗、业务影响、责任归属及公司正式评价仍需证据。这些建设与 C05 的公司复盘发现分别记录，尚未明确是否直接来自那次复盘的整改。

### C07 — Project S：创始人推动的项目受限于权限与工作流程设计

**行动与目标：** 2026 年 4 月，一位米哈游创始人开始亲自推动 Project S。它基于 Claude Code，做了我所说的“harness 工程”，并打通办公 IM。最终目标是将一个团队或部门中每个人的工作流程都迁入 Project S；这是目标，尚不是已经完成的迁移结果。

**记忆、权限与办公入口：** 设计希望基于人与人、人与 agent 的工作对话、会议、文档等材料构建团队级 agent memory。来自成员工作流程的记忆对整个团队可见，agent 的访问模型赋予它每位团队成员的数据权限。将所有办公入口集中到 IM，是为了让 Project S 获取这些工作流程的全部上下文。这些能力和权限在米哈游实际部署到何种程度仍待补充。

**Anuttacon 对照：** 据我了解，创始人先在自己的另一家 LLM 公司 Anuttacon 推行项目。我将 Anuttacon 描述为权限体系相对简单的初创公司，这使推进更顺利。这是我对差异的解释；本次回顾尚未提供已完成的流程迁移、采用指标及业务结果。Anuttacon 的官方自述见 S05，但不佐证 Project S 或创始人关系。

**米哈游的结果与我的评价：** 预期的推广未能在米哈游推进。我认为其错综复杂的权限体系是最大的实施障碍，也认为项目非常理想化：基于员工工作形成对团队全员可见的记忆，以及为了获取完整上下文而将所有办公入口集中到 IM，对这里的情况都过于激进。这些是我对推进困难的解释，并非有记录的公司复盘结论。项目最终状态、试点范围及是否仍有部分功能在使用，尚待澄清。

### C08 — 基于 OpenCode 的开发、部署与验证框架

**能力与背景：** 5—7 月，一个部门项目基于 OpenCode 二次开发了 agent 框架，提供端到端开发、部署、上线能力。我认为它是公司内很受欢迎的部门项目之一。项目名称和负责部门仍待补充。

**我观察到的采用：** 起初研发以外的同事很喜欢使用它。后来，随着它增加了我所说的 agent 端到端验证能力，研发同事也有了一定接受度。我将这种接受变化与新增能力联系起来；这尚不是覆盖全体研发的采用指标，也不能证明验证是唯一因素。

**验证能力：** 框架同时提供前端和后端部署，因此研发可以直接让 agent 通过 browser use 或 Playwright 验证产物。这明确了可用的验证方式；具体的一次执行、检查内容和结果仍待补充。

**待补证据：** 代表性验证任务及验收标准、上线与采用日期、实际交付项目、人工参与、质量与运行成本，以及持续使用情况。具备从开发到上线的能力，尚不能证明每个任务都成功完成或全程无需人工参与。

### C09 — 我推进的个人 agent 记忆迁移项目

**我的参与与要解决的问题：** 这一时期，我推进了一个部门级记忆系统项目，解决个人在多个端、多个 agent 之间协作的问题。在我看来，它也是公司内很受欢迎的项目。

**系统实现的能力：** agent 的记忆可以从一个端迁移到另一个端，也可以从一个 agent 迁移到另一个 agent。这一能力支持个人在不同环境之间延续工作。它与 C07 的团队全员共享记忆目标在范围上不同；两个项目的技术或组织关系尚未明确。

**结果与待补证据：** 系统支持记忆迁移，我观察到它在公司内受到欢迎。支持哪些端和 agent、迁移的记忆内容、迁移机制、权限、典型任务、采用指标和对任务完成的影响仍待补充。它与 C01 中我入职时参与的数据团队项目的关系也待明确。

## 我的观察与判断

我认为，相比一线互联网公司，尤其是字节跳动，米哈游在 LLM 和 agent 应用方面起步明显偏晚。这是基于上述经历的个人比较判断，不是行业排名或量化成熟度评估。

考虑到公共团队负责人的职级，我将 12 月的讨论视为在一定程度上反映高层想法。这一理解不能确定存在正式的全公司授权或所有高层的一致意见。

我认为 Echo 是重大转折，也是公司层面的采用成功。我的解释主要在于客户端 UI 降低了使用门槛，尤其是对非研发员工而言。这是我的判断，并非有记录的公司评价或经测量得出的因果结论。

我将随后两三个月描述为公司非常激进地推广应用、大量投入的阶段。“无需继续研发通用 agent”以及“成本事件属于必要探索代价”，是我所理解的公司立场。我参与了事件复盘，上述限额、路由、缓存及协作基础设施方面的发现记录的是公司的反思。我个人对这些立场的支持、保留意见和事后反思仍待展开。

我对 3—4 月 MCP 建设的评价是：广泛覆盖与较低的接口质量、尚未解决的权限设计并存。我将可用性问题与直接封装现有服务 API 联系起来；读取数据时，反复分页调用消耗了大量上下文。这些是我的观察与判断，并非有记录的公司共识。

我对这一阶段的整体判断是，公司强调人人都可以创造 agent，却忽略了从公司层面提供共享 AI 原生基础设施。我将这一缺失与 3—4 月大家普遍感到 AI 项目推进不及预期联系起来。在此期间，部门 OpenClaw 部署几乎全部停用，但各自的停用原因尚未记录。这是我对目标与落地差距的评价，并非有记录的公司结论或覆盖所有项目的量化结果。

我认为 Project S 是一个非常理想化的项目，创始人于 4 月亲自参与推动，体现了公司延续的激进态度。我对推行差异的解释主要在于 Anuttacon 权限较简单，而米哈游权限复杂得多。我认为让工作中形成的记忆对全团队可见、把所有办公入口集中到 IM，对米哈游都过于激进。这与公司的正式评价分别记录，后者尚未补充。

我将 5—7 月描述为公司层面推广态度趋缓、一线和部门普遍推进 harness 工程与基建完善的时期。我观察到了 MCP 重构，以及检索、权限和记忆能力的补充。我也认为 OpenCode 二开框架和我推进的记忆项目在公司内很受欢迎。框架起初受到非研发同事喜爱、后来获得研发一定程度接受，属于采用感受方面的观察；量化交付收益和早期问题解决程度仍待明确。

我加入米哈游时，认为 Claude Sonnet 4.5 是当时最优秀的模型。[Anthropic 发布公告](https://www.anthropic.com/news/claude-sonnet-4-5)确认其发布日期为 2025 年 9 月 29 日。这支持时间背景，对模型优劣的评价则属于我个人。

我对字节跳动工具的正面评价针对某些长任务。可靠性、任务时长、人工介入和业务影响仍需展开；我了解其在 2025 年底情况的依据也待补充。这段回顾不代表我在当时仍就职于字节跳动。

## 跨案例的待验证假设

以下假设属于待我审阅、并需进一步证据支持的分析草案，与上文的个人判断及米哈游自身的结论分开。

**上手门槛与采用：** Dify 受到的关注有限，而 Echo 获得广泛使用，由此可提出一个假设：除了平台是否可用，开始使用所需的成本也可能影响采用。这一假设参考了我对 Echo UI 的解释。两者的用途、用户群、推广条件和观察时段尚未对齐，不能据此确定客户端 agent 普遍优于服务端平台。

**研发投入的方向：** 阶段线索从共享平台讨论和客户端 agent 采用，发展到激进复用框架与 skill、部门部署大范围停用，再到 5—7 月的 harness 与基建建设。C04—C09 为检验哪些共享能力和公司级职责支持员工创建的 agent 持续运行提供了依据。这一过程尚不能确定各项目停用或公司态度变化的原因、对 12 月方案和 Echo 的影响，以及每项投入对后续结果的贡献。

**从任务到流程：** C04 区分了单点任务采用与预期的跨员工工作串联。需要检验的是：完备的 skill 能否支持可靠的工作交接和完整流程。更多项目和 skill 本身不能证明这一结果。

**探索与成本：** C05 同时体现了承担高额探索成本的意愿，以及公司对限额逻辑、路由与缓存效率、协作基础设施的反思。结合 C04，可进一步检验：复用通用框架和 skill 时，还需要哪些支持基础设施？复盘发现、实验价值和后续整改效果需要分别评估。指出缺陷，还不能说明缺陷已经修复，或实验取得了什么价值。

**MCP 覆盖与可用权限：** C06 提示，需要将接入覆盖面与任务完成、上下文消耗及权限可用性分别评估。后续重构和能力补充为改进前后的对比提供了基础。无论广泛覆盖还是重构规模，都不能单独证明工具和权限模型已能支持完整流程。

**团队 agent 的跨组织迁移：** C06 和 C07 提示，在将初创公司的进展作为大型组织的参考前，需要检验既有权限和办公习惯如何影响采用。agent 对源数据的访问权限，与每位员工对生成记忆的访问权限，是不同的设计决策。Project S 的对照提出了这些问题，但尚未单独识别各因素的影响，也不能据此判断团队记忆本身不可行。

**Harness 实践与验证：** 5—7 月对上下文和交付基建的关注，结合 C08，提出了一个问题：在现成 agent 之外，还需要什么条件才能使长任务可靠完成？C08 将前后端部署与 agent 通过 browser use 或 Playwright 验证产物联系起来，也提示这一能力可能影响研发接受度。检验这些假设仍需要具体的验证任务和结果，尤其是涉及多人或多个 agent 的工作。

**个人记忆迁移与团队记忆：** C09 解决个人跨端、跨 agent 的工作连续性，C07 则希望让工作中形成的记忆对全团队可见。两个案例提示，可以将可迁移性与共享可见性作为不同需求评估。C09 受到欢迎，尚不能证明它解决了 C07 的组织与权限难题。

## 面向当前公司的决策选项

以下选项基于上述案例形成，仍待我审阅，并结合当前公司的优先事项和约束进行评估。它们尚不是最终建议，也不代表米哈游已经实施的措施。

- **扩大采用——C03：** 如果希望让非研发员工更广泛地使用 agent，可选择少量代表性任务，试用容易上手的通用智能体界面。扩大应用前，评估完成首个有用任务的成本、重复使用情况和任务质量。
- **框架与 skill 复用——C04：** 如果正在考虑这一路线，可通过有代表性的跨员工交接检验完整流程。将一组 skill 视为完整流程之前，评估完成质量和所需人工介入。为任务暴露出的共享基建缺口明确公司级负责人，并在上线后跟踪持续使用和流程完成情况。现有案例尚不足以支持停止所有内部通用 agent 研发。
- **实验消耗与基础设施——C05：** 设置实验预算和网关用量上限，限制 agent 数量和相互传递的消息历史，在达到指定阈值时暂停或复核。评估路由和 KV cache 命中率，明确多 agent 与 A2A 协作所需的基础设施。将费用、预期取得的认识、实际结果及整改效果一并记录。阈值和基础设施优先级应结合当前公司的资源与目标制定。

- **MCP 质量与权限——C06：** 用有代表性的 agent 任务评估接口，包括通过分页接口读取数据所需的调用和上下文。明确个人和团队 agent 可访问的系统，并在同一任务评估中验证这些权限边界。根据完成质量、上下文消耗和权限问题，指导接口与权限的改进。

- **团队工作流与记忆——C07：** 从明确的团队和有限的工作流程开始。规定 agent 的数据权限及各部分记忆的可见人员，再评估任务结果与改变现有办公习惯所需的成本。在要求整体迁移前，评估把工作移入 IM 是否改善完成情况。待试点范围内的权限和流程问题得到解决后再扩大。

- **长任务交付与验证——C08 及 5—7 月阶段：** 选择一个覆盖开发、部署和上线的代表性任务，明确提供给 agent 的上下文、必须验证的结果，以及人与人或 agent 之间的交接。扩大使用前，评估完成质量、人工介入及目标用户群的接受情况。

- **个人记忆迁移——C09：** 用一个切换到另一端或另一 agent 继续执行的具体任务进行验证。明确需要迁移的记忆及访问边界，再评估工作连续性和重新交代上下文所需成本。如果需要团队共享，则单独评估。

评估应区分基础设施是否可用、应用覆盖面、实际使用、流程完成情况，以及成本与结果的关系。C03 记录我对 Echo 采用成功的评价，C04 涵盖早期采用和后续大范围停用。C06 记录推广问题及后续重构，C07 涉及组织适配。C08 补充交付和验证能力演进中的接受变化，C09 补充个人记忆可迁移性。项目受欢迎和能力可用，仍需与量化业务价值建立联系。
