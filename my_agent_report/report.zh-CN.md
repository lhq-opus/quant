# Agent 推广与项目落地：米哈游的经验

**语言：** 简体中文 | [英文版](report.md)

**状态：** 工作草稿——覆盖早期基础设施、Echo 采用、后续激进扩张及一项据述的探索成本事件；流程结果与分析仍不完整。

**读者：** 作者当前公司的管理层。

**目的：** 回顾米哈游及其数据团队在 agent 推广和项目落地方面的实践，为当前公司的 AI 决策提炼经验。作者更早任职的字节跳动提供比较背景。

**回顾时间范围：** 计划回顾一年的经历，但确切起止时间仍待确认。米哈游的回顾始于作者 2025 年 11 月入职，涵盖作者所述的 2026 年 1 月 OpenClaw 热潮之后 Echo 的出现，并延伸至随后两三个月。Echo 的日期及后续阶段的具体起止月份仍待补充。字节跳动的对照经历涉及 2023 年底至 2025 年底。

## 执行摘要

作者于 2025 年 11 月加入米哈游时，据其了解，全公司的 agent 项目很少，其在数据团队参与的工作正是其中之一。作者还回顾，公司内部已有私有化部署的 Dify，但在其所观察的整个时段内受到的关注有限。

到 12 月，据作者回顾，公司层面的 agent 基建只有 LLM 网关和 Dify，另有零星几个 agent 项目。作者与米哈游公共团队负责人讨论了服务端通用 agent 平台、skill hub 和知识库，目标是在未来几个月支持员工的业务流程和端到端工作。这是一段规划讨论；批准、资源投入、实施及结果尚未明确。

后续的一个转折是 Echo，一个运行在员工客户端上的通用智能体。据作者回顾，2026 年 1 月 OpenClaw 在国内走红之后，另一个项目团队独立、自发发起了 Echo。作者观察到它在米哈游被广泛使用，尤其受到非研发人员欢迎，认为该项目在公司层面很成功，并将其采用归因于客户端 UI 大幅降低了上手成本。量化的任务结果仍待补充。

随后两三个月，作者将公司的推进方式描述为非常激进：部门层面出现至少四到五个 OpenClaw 二次封装项目，员工大规模将单点任务迁移至 agent，并接入办公 IM chatbot。据作者转述，公司认为现成框架已使继续研发通用 agent 变得没有必要；员工应编写足够完备的 skill，最终把单点任务串成覆盖所有人工作的完整流程。这属于当时的目标；现有素材描述的是单点任务的采用，尚未证明更广泛的流程目标已经实现。

作者称公司投入了相当大的成本，一位员工使用 Claude Opus 4.6 探索多 agent 协作时，在网关未限量、agent 数量和 agent 间历史消息数据量未受限制的情况下，一天产生了人民币 200 万元的 token 费用。据述，公司将此事件视为探索 LLM 的必要代价。金额、机制和公司回应均归因于作者；目前尚未提供账单记录、实验结果及后续限制措施。

作者认为，米哈游在 LLM 和 agent 应用方面的起步明显晚于字节跳动。据其回顾，字节跳动从 2023 年底在客服和内部研效中使用 LLM，逐步发展到 2025 年底已有工具能够完成某些长任务。详细结果及差异的原因仍待明确。

### 2025 年 12 月——共享 agent 平台的讨论

作者与米哈游公共团队负责人进行过交流，并描述其职级为“公司创始人-1”。公共团队在英文中暂译为 shared team，正式英文名称尚未确认；职级描述不等于明确的汇报关系。

讨论涉及如何在未来几个月建设以下能力：

- 在服务端运行的通用 agent 平台。
- 包括 skill hub 和知识库在内的支持基础设施。
- 支持员工把自己负责的业务流程迁移到平台，或借助平台更好地完成端到端工作。

这些属于讨论中的能力与预期用途。现有素材尚未明确已约定的行动项、项目负责人、资源、承诺的排期或交付结果，也未说明新平台将扩展、替代 Dify，还是与其并存。作者将这次对话视为部分反映高层想法的判断，记录于下文。后续决策与组织反思仍待补充。

### 2026 年 1 月 OpenClaw 热潮之后——Echo 与更广泛的采用

作者将 Echo 视为员工使用 agent 情况的一次重大变化，并已澄清它来自另一个项目团队的自发探索，独立于 12 月的平台讨论。因此，两条项目线有不同的起源。它们后来是否共享基础设施，以及服务端方案如何推进，仍待补充。

所述变化涉及内部团队的主动探索和员工的广泛采用，尤其是研发以外的员工。针对 Echo 的具体支持与后续决策仍待补充。案例 C03 记录了采用结果及作者的解释；下一阶段描述公司态度在更大范围内的变化。

### 随后两三个月——围绕现成框架与 skill 的激进扩张

作者描述，公司对 LLM 和 agent 的投入意愿显著增强。部门团队推出了至少四到五个 OpenClaw 二次封装项目。员工开始大规模将零散、单点工作迁移至 agent，并接入办公即时通信 chatbot。项目名称、部门、IM 产品，以及项目计数是否包括 Echo，仍未明确（C04）。

据作者转述，公司的立场是：市场已有足够好的框架，一切通用 agent 都没有必要继续研发。预期的投入方向是复用这些框架，让员工编写完备的 skill，最终将单点工作逐步串成跨员工的完整流程。这一立场的来源与正式适用范围正在澄清。目前尚未明确具体项目的取消、12 月平台计划的完成情况，或全公司工作流程已成功串联的结果。

据述，公司为此投入了大量资源。在此期间，一位员工的多 agent 实验一天产生了 200 万元人民币的 token 费用。作者称公司最终将其定性为探索 LLM 的必要代价（C05）。这是作者转述的公司事后评价；作者本人是否认同尚未提供。本阶段和事件的确切日期仍待补充。

### C03 — Echo：获得广泛使用的客户端通用智能体

**背景与起源：** 作者将 Echo 的出现放在 2026 年 1 月 OpenClaw 在国内走红之后。另一个项目团队独立、自发发起了这项探索。Echo 的启动、首次上线和更广泛推广的日期尚未提供，因此不能由 1 月的背景推定它在 1 月上线。

**所述产品与行动：** Echo 是运行在用户客户端上的通用智能体。作者将其产品形态类比为 Kimi Claw，并回顾性地类比为提供本次素材时的 ChatGPT 客户端。这些是概括性的产品类比；Echo 的实现方式和技术依赖仍未明确。运行在客户端不等于已确认模型推理完全在本地进行。

**观察结果与分类：** 作者称 Echo 在米哈游内部被广泛使用，尤其受到非研发人员欢迎，并认为它在公司层面非常成功。本案例记录为作者评价的采用成功。目前尚未提供用户数、采用比例、留存、具体任务，以及生产力或业务结果。

**作者的解释：** 客户端 UI 大幅降低了上手成本，作者将其视为获得广泛使用的原因。这是作者对观察结果的解释；目前尚未提供对比上手成本的测量，或能够单独识别 UI 影响的证据。

**尚缺信息：** 团队身份、具体用户流程、分发与支持、公司针对 Echo 的后续决策，以及与共享基础设施的连接仍待明确。12 月方案后来的状态是另一项尚未回答的问题。

### C04 — 部门级 OpenClaw 封装与通过 IM chatbot 执行的任务

## 作者个人看法

作者认为，相比一线互联网公司，尤其是字节跳动，米哈游在 LLM 和 agent 应用方面起步明显偏晚。这是个人比较判断，并非全面的行业排名或量化成熟度评估。

考虑到公共团队负责人的职级，作者认为 12 月的讨论在一定程度上代表了当时高层对 agent 的态度与规划。这提供了一个高层相关视角，尚不能据此认定存在正式的全公司授权或所有高层的一致意见。

作者将 Echo 视为重大转折和公司层面的成功案例，着重强调客户端 UI 如何降低使用门槛，尤其是对非研发员工而言。这一评价属于个人判断，与有记录的公司评价或经测量得出的因果结论予以区分。

作者将随后两三个月描述为公司非常激进地推广应用、大量投入的阶段。“无需继续研发通用 agent”及“高额成本属于必要探索”的解释，在其叙述中均属于公司看法。作者个人对此的支持、保留意见及事后反思仍待记录。

作者回顾，在其入职时，自己认为 Claude Sonnet 4.5 是当时最优秀的模型。Anthropic 的公告确认该模型于 2025 年 9 月 29 日发布，早于该入职月份。发布日期支持时间背景；对模型优劣的评价仍归因于作者。参见 [Anthropic 发布公告](https://www.anthropic.com/news/claude-sonnet-4-5)。

作者对字节跳动工具的正面评价针对某些长任务。可靠性、任务时长、人工介入程度和业务影响尚未明确。作者如何了解这些工具在 2025 年底的情况也仍待补充；报告不假定其当时仍在字节跳动任职。

## 跨案例经验

Dify 受到的关注有限，与 Echo 据述获得广泛使用，构成了一项可继续研究的初步假设：除了平台是否可用，员工开始使用所需的成本可能也是影响采用的重要因素。这是结合作者对 UI 的解释形成的整理者分析，并非已有记录的公司反思。目前尚未对齐两类产品的用途、用户群、推广条件和观察时段，因此不足以得出客户端智能体普遍优于服务端平台的结论。

现有回顾已形成一条阶段线索：共享平台讨论，另一个团队推出容易上手的客户端产品，随后是部门激进复用外部框架并由员工编写 skill。后续的公司立场强调研发投入应放在哪里。它如何影响 12 月方案及 Echo 的路线仍待明确；仅有时间先后，也不能证明 Echo 导致了所有后续决策。

**从单点任务到连贯流程：** C04 区分了已观察到的任务采用扩张与预期的跨员工工作串联。整理者认为，需要检验的关键主张是：足够完备的 skill 能否支持可靠的工作交接与完整流程。更多项目和更多 skill 本身还不能证明这一结果，仍需有代表性的流程成效。

**探索意愿与成本控制：** C05 同时呈现了公司据述愿意承担高额探索成本，以及具体的用量限制缺失。整理者据此提出，应分别评估探索的价值和为每次实验限定消耗的方法。公司接受此事件，并不能说明该支出取得了哪些认识，或同样结果是否能够以更低成本获得。

## 对当前公司的启示

**由 C03 提出的暂定选项：** 如果当前公司希望让非研发员工更广泛地使用 agent，可以用少量有代表性的员工任务试用容易上手的通用智能体界面。在决定如何扩大应用前，评估完成首个有用任务的成本、后续使用情况和任务质量。这是整理者提出的建议，并非米哈游已实施的行动或已得出的结论；是否适用取决于当前公司的需求与约束。

**由 C04 提出的暂定选项：** 如果正在考虑复用通用框架并由员工编写 skill，可以用有代表性的跨员工交接检验完整流程。在把一组 skill 视为完整流程之前，评估完成质量和所需的人工介入。目前案例还不足以支持一概停止所有内部通用 agent 研发的决定。

**由 C05 提出的暂定选项：** 为多 agent 实验设置预算与网关用量上限，限制 agent 数量和相互传递的消息历史，在达到指定阈值时暂停或复核。将每次实验的费用、预期取得的认识和实际结果一并记录。这些是针对所述事件提出的建议，并非已知米哈游实施的措施；阈值应结合当前公司的资源与目标制定。

更完整的评估应区分基础设施是否可用、应用覆盖面、实际使用情况、流程完成情况，以及成本与结果的关系。Echo 和部门项目目前提供的是关于采用的回顾性证据；持续使用和业务价值仍需后续素材支持。
