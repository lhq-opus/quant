# Agent 推广与项目落地：面向 AI 决策的经验

我正在为当前公司的管理层准备这份报告，回顾我在米哈游的 agent 开发工作及对公司推广实践的观察，并以更早在字节跳动的经历作为比较背景。报告以我的第一人称口吻向上汇报，同时维护对应中文版，便于我核对完整性和表述。

阅读[工作报告](report.zh-CN.md)。

[英文阅读说明](README.md) · [英文报告](report.md)

**状态：** 工作草稿。内容覆盖米哈游 2025 年 11—12 月的基线与共享平台讨论、Echo 的独立出现及我对其采用成功的评价，以及随后两三个月的激进扩张。案例包括我在数据团队的工作、Dify 受到的关注有限、Echo 的广泛使用且尤其受到非研发员工欢迎、至少四到五个部门级 OpenClaw 封装，以及接入办公 IM chatbot 的单点任务。

报告还涉及公司强调现成框架和员工编写 skill、串联跨员工工作的目标，以及大量投入。据我了解，一次使用 Opus 4.6 的多 agent 实验一天产生 200 万元人民币费用，公司将其视为必要的探索代价。我参与了公司复盘，其中指出网关限额逻辑不完善、路由问题导致 KV cache 命中率低，以及缺少支持多 agent 和 agent 间（A2A）协作的基础设施。整改及结果、框架与 skill 立场的来源、量化流程结果及我个人对这些立场的评价仍待补充。公开来源仅支持外部产品时间线。

2026 年 3—4 月的经历补充了基础设施的快速建设，几乎所有内部系统都设计了 MCP。我认为绝大多数实现质量低，往往直接封装现有服务 API，未充分针对 agent 调整。读取分页数据需要反复调用 MCP、调整参数，消耗大量上下文。个人和团队 agent 的权限问题在我的观察期内一直未解决。上线覆盖面、负担测量、任务结果及权限问题的持续时间仍待展开。

字节跳动提供从 2023 年底至 2025 年底的比较背景。完整回顾日期和当前公司的约束仍待明确。容易上手的界面、流程验证、实验消耗、支持基础设施，以及 MCP 可用性和权限等分析假设与选项保留为待我审阅的草案，与已经表达的个人判断分开。
